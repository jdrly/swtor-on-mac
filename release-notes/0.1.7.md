## SWTOR on Mac 0.1.7

Graphics driver fixes against GPU faults and anti-aliasing lines on M1–M4 Macs, a possible fix for a startup crash on an M1 Mac with macOS 26.1, clearer logs when something goes wrong, a new experimental setting, and the same shader cache as 0.1.6.

### Fewer ways for the GPU to fault
A GPU fault can end the game or, at worst, log you out of macOS. The graphics driver closes several
paths where the GPU could read memory the game never gave it, or read it at the wrong time:
- A texture slot the game left empty no longer points at nothing: it gets an empty texture of the
  kind the shader expects (d9mt #133, #137).
- Some of the game's shaders read a cube texture (six faces) where the game sometimes binds a flat
  one. Metal's validation flags that as an invalid binding. Such a slot now gets an empty cube
  texture (#151).
- Vertex data that should repeat, or that is shared per instance, no longer runs past its buffer, and
  draws that ask for more vertices or instances than the game supplied are cut to what is there
  (#135, #136).
- Every compiled pipeline is registered with Metal as resident, as Apple asks Metal 4 apps to do
  (#147).
- A copy after a render pass now also waits for that pass's vertex work (#148).

None of these is proven to be the cause of the GPU faults a few players saw. If one happens again,
please send the logs (see *If something goes wrong*).

### Anti-aliasing lines on M1–M4 Macs
With the game's highest anti-aliasing, an M4 Mac showed flickering lines and specks. On M1–M4 Macs
the driver now turns the GPU's lossless texture compression off for anti-aliased textures and the
textures they are resolved into (d9mt #140). M5 Macs and play without anti-aliasing are unchanged.
With anti-aliasing on, a copy of part of the picture also lands at its place now, instead of the
whole picture landing in the top-left corner (#125).

### A possible fix for a startup crash on an M1 Mac with macOS 26.1
On an M1 Pro with macOS 26.1 the game closed on its own a few seconds after it started, and the
log said only `exit code 148`. The crash was inside Apple's Metal code, while the driver built its
first pipeline. The driver now describes its pipelines to Metal the way a native app does: it
leaves out the colour outputs and vertex buffer slots a pipeline doesn't use (d9mt #156, #157).
What the game draws doesn't change. This is a possible fix: we couldn't reproduce the crash on our
Macs, and it isn't confirmed on the affected Mac yet. If your game still closes at the start, please
send the logs.

### Two rare freezes
Two cases where the game could freeze without a crash or a log line, both fixed in DXVK long ago:
a large texture or buffer update right after the driver sent a frame to the GPU (d9mt #138), and
several game threads waiting on the driver at once (#139).

### Fewer GPU Batches (Experimental)
A new setting in *Settings > Graphics*, off by default. It sends each frame to the GPU in fewer,
larger batches, so less data moves through memory. It may help MacBook Airs and base M1–M3 Macs,
and it may cost frame rate on others. If you try it, tell us how it went on your Mac. `wine.log`
says `SWTOR on Mac flush cap: on` while it's on.

### Clearer logs when something goes wrong
- When the GPU fails a frame (a page fault, a timeout), `wine.log` gets a `D9MT-GPU-ERROR` line
  that names the error (d9mt #134).
- When the game crashes, `wine.log` gets a `D9MT-FATAL` line before the game's own crash handling
  runs: what kind of crash it was, in which file and where in it, and what the driver was doing
  last. `d9mt: image` lines near the start of the log map a crash in Apple's code to the library it
  happened in. Both only record and never change what happens (#155).
- `wine.log` starts with the graphics settings, the power and thermal state, and short fingerprints
  of the graphics driver's files.
- With *Debug Logging* on, a `SCREEN` line each second says how many frames macOS actually showed
  and how long they took to reach the screen, and `HITCH` lines say when they happened and whether
  the game window was on screen (#154). The driver's profiler uses a cheaper clock (#141). With
  *Debug Logging* off, none of this runs.

### Collect Logs
- The zip now has `system-reports/`: short extracts of macOS's own reports from when a Mac logs
  you out, freezes or restarts (the GPU's fault reports for the game, WindowServer restarts,
  kernel panics), from the last 48 hours or since the game last started. Only known lines, with
  other apps' names left out.
- The session report no longer calls per-second figures a "1% low" or "99th percentile", and says
  which numbers it can't measure. `sessions-compared.txt` puts the last few game starts side by
  side.

### Your compiled shaders stay
The code that compiles the game's shaders is the same as in 0.1.6 (AIR codegen `38243f7b`, lineage
0.1.5.1), so 0.1.7 opens 0.1.6's shader cache as it is and recompiles none of them. Metal keeps a
cache of its own for the finished pipelines, and the changes above alter how some pipelines are
described, so the first start after updating, and the first visit to a busy place, may stutter a
little while Metal builds those pipelines once.

### Known issue: a rare freeze
Rarely, the game freezes: the window stays black or still and the pointer turns into a spinning
wheel. `wine.log` then has a `rosetta error: failed to send exception` line. It happens in Rosetta,
below the graphics driver, and was already seen with 0.1.6. Force quit the game (Option-Command-Esc)
and start it again; please choose *Collect Logs…* first and send the zip.

### If something goes wrong
If the game freezes, closes, or the Mac logs you out, open SWTOR on Mac, choose *Collect Logs…* before
you start the game again, and send the zip.

### After updating
Open SWTOR on Mac and click *Update to 0.1.7* in the window, with the launcher and the game closed.
From 0.1.4 or newer it takes under a minute and downloads nothing. Your game settings, key
bindings and SWTOR on Mac's settings stay.
